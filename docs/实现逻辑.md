# Spec Mode 实现逻辑

## 模块划分

| 文件 | 职责 |
| --- | --- |
| `index.js` | 入口。注册投影、提示词段落、`/spec` 命令、`spec_resolve` 工具、只读守卫、AGENTS.md 警告、跨会话提醒 |
| `state.js` | 状态类型、会话投影单元、草稿路径解析 |
| `guard.js` | 路径分类谓词、工具入参路径提取 |
| `advisories.js` | AGENTS.md 软约束文案 |
| `prompt.js` | 注入文本（访谈协议、跨会话提醒） |

依赖方向单向：`index → {state, guard, advisories, prompt}`，其余模块互不依赖。
四个被依赖的模块都是纯函数/纯数据，`selftest.mjs` 直接测它们，不需要 Host。

## 状态模型

```js
{
  active: boolean,                              // 已提交的启用状态
  running: { commandId, wanted } | null,        // 正在执行的那条 /spec 选择
  exitCall: string | null                       // 正在评审的 spec_resolve callId
}
```

注册为会话投影单元 `spec`（`stateVersion: 1`），**host-only**：不声明 `wire.view`，
所以不参与客户端可见的投影快照，但会被投影缓存正常 checkpoint / restore。

### 为什么必须 fold 既有事件，而不是自建会话条目

原插件用宿主提供的自定义会话条目 API 写状态。DSH 不能这么做：

- `SessionEventMap` 是可声明合并的，TS 层面能声明新类型；
- 但**读路径**只接受 `KNOWN_SESSION_EVENT_TYPES`（由 `scripts/gen-persistence-catalog.ts`
  生成的闭集）里的类型，除非事件信封带 `ignorable: true`；
- 而 `Session.append()` 无法设置该标记。

结论：写自定义类型会让这份会话日志之后**打不开**。所以状态全部从既有事件推导：

```
command/run   name === "spec"        → running = { commandId, wanted: args.trim() !== "off" }
command/done  配对 commandId          → kind === "success" ? active = running.wanted : 丢弃
                                       两种情况下都清 running
tool/call     name === "spec_resolve" → exitCall = callId
tool/result   配对 exitCall           → isError ? 清 exitCall（用户拒绝）
                                                 : { active: false, running: null, exitCall: null }
其它事件                               → 返回同一个 state 引用
```

`apply()` 是纯同步 fold，对无关事件返回**同一个引用**（投影契约要求，`Object.is` 相等
即零下游工作），state 是纯 JSON（缓存前提）。

### 有效状态 vs 已提交状态

两个读法，不能混用：

| 函数 | 读法 | 谁用 |
| --- | --- | --- |
| `isSpecActive(session)` | `running?.wanted ?? active` | 守卫、提示词段落、退出工具 —— 问「这一刻算不算在 spec mode 里」 |
| `loggedActive(session)` | `active` | `/spec` 命令 handler —— 问「这条命令进来之前是什么状态」 |

**`command/run` 在 handler 之前入日志**（`dsh-commands` 的 `execute()` 先 append
`command/run`，再调 handler，最后 append `command/done`）。所以 handler 执行期间
`running.wanted` 已经是本次选择，而 `active` 还是旧值。实测踩到过：

- `/spec off` 若用 `isSpecActive` 判「本来是否开启」，会得到 `false`，错报
  `Spec mode 未开启。`；
- `/spec` 若用 `isSpecActive` 判「是否已在模式里」，会因为 `running.wanted === true`
  而跳过 plan mode 互斥检查。

`selftest.mjs` 里有一条断言专门锁这个不变量。

### 进程内旁路

`liveExits` 是一个 `WeakSet<Session>`：退出工具批准后加入，`/spec` 再次进入时删除。

它只解决一件事：批准退出的 `tool/result` 入日志后，**同一轮**紧接着的 `write AGENTS.md`
不能被「还没 fold 到」的投影拦下。durable 真相仍是 `tool/result` 的 fold——旁路只影响
本进程的即时判定，进程重启后由日志恢复。

## 生命周期绑定

```
agent/created      → 未完成草稿提醒（仅根会话、且当前未启用、且草稿非空）
tools/post-execute → AGENTS.md 行数检查
```

投影本身**不自己订阅** `session/event`：`ctx.sessionProjections.register()` 之后由框架
驱动 fold，所以没有需要清理的订阅。其余注册（`ctx.tools.register`、`ctx.tools.guard`、
`ctx.systemPrompt.section`、`ctx.on`、`ctx.inject`）都挂在插件自己的 fiber 上，卸载即回收。

子代理的判定用 `session.header`：`origin === "subagent"` 或 `delegationDepth > 0` 都不是
访谈者，不发提醒。子代理的 spec 状态天然是 false（它的日志里没有 `/spec` 记录），
所以守卫也不会拦它。

## tool guard

`ctx.tools.guard()` 是**同步、单调**的检查：返回字符串即拒绝，返回 `undefined` 放行；
它排在所有 `tools/pre-execute` listener 之后，所以没有后续 listener 能把拒绝翻回允许。

```
exec.agent 缺席                                    → 放行
该会话 isSpecActive === false                      → 放行
targets = extractTargetPaths(exec.arguments)       → 键：file_path / filePath / path / paths[]
├─ 工具名匹配 /^(delete|remove|move|rename)/i
│    任一 target 分类为 "draft"  → 拒绝（草稿在合并前不可删改）
│    否则                        → 放行
├─ 工具名不是 write / edit       → 放行
└─ 任一 target 分类为 "working-tree" → 拒绝
      否则                        → 放行
```

守卫注册在**全局** context 上（不是 `agent.ctx`），按 `exec.agent.session` 取状态——
这正是「状态按会话分键」的落点。

### 路径分类（`classifyTarget`）

```
raw 为空，或匹配 /^[a-zA-Z][a-zA-Z0-9+.-]*:\/\//  → "protocol"      （local://、artifact:// …）
resolve(cwd, raw) 抛错                              → "working-tree"  （fail closed）
absolute === draftPath                              → "draft"
其余                                                 → "working-tree"
```

**`draft` 只匹配草稿文件本身，不匹配其父目录。** 草稿住在项目的 `docs/` 里，目录级放行
等于把真实文档目录开了写权限。父目录由 `ensureParentDir` 用 `mkdirSync` 直接创建，
不经过工具层，所以不需要放行。

分类只按会话 cwd 解析相对路径。宿主写文件时可能改用沙箱 workspaceRoot 作基准，两者不同
时相对路径会指向另一个文件——协议因此要求一律写绝对路径。这是已知边界，不是疏漏。

## 草稿路径解析

```js
findProjectAnchor(cwd)  // 最近的 .git → 都没有则 cwd
resolveDraftPath(cwd)   // join(anchor, "docs", "spec-draft.md")
```

锚点规则**故意**与 `@deepseek-ai/dsh-agent-instructions` 保持一致（它的
`projectRootMarkers` 默认 `['.git']`，找不到就用会话 cwd），这样草稿和指令文件落在同一个
项目里。

原插件还会认「项目本地配置目录」，并专门排除用户全局配置根。DSH 没有对应的项目标记
（`.dsh` 是 harness home，不是项目标记），所以这条分支不引入——也就没有「全局配置根被
误当项目标记、草稿写进 `~/docs/`」那个坑。

## 注入机制

访谈协议走**系统提示词段落**，不走消息注入：

```js
ctx.systemPrompt.section({
  name: "spec:policy",
  order: ctx.systemPrompt.getSectionOrder("PLAN_POLICY"),   // 500
  text: (context) => isSpecActive(context.agent.session) ? specModeContext(draftPath) : "",
});
```

- 未激活时渲染空串，宿主会丢弃空段落——**不激活就零 token**；
- `text` 是每次 assembly 求值的 provider，不是快照，所以进出模式立即生效；
- provider 包了 try/catch，抛异常会让整个 assembly 失败，这里选择「贡献空串」。

用户可见的两条消息用 `agent.inject()` / `agent.steer()`：

| 场景 | 调用 | 效果 |
| --- | --- | --- |
| `/spec <想法>` | `agent.steer(userMessage([...attachments, text]))` | 想法成为这一轮的用户消息并唤醒 driver |
| `/spec`（无参） | 无 | 只切模式，不提交任何消息 |
| `/spec off` | `agent.inject(noticeMessage(...))` | 只入 inbox，不唤醒；下一轮模型知道模式已退出 |

`/spec`（无参）**不合成起轮消息**：命令面本身不产生模型消息，所以裸 `/spec` 之后没有任何
一轮被唤醒，访谈从用户真正写下的东西开始——`/spec` 后面的想法，或他随后发的第一条普通
消息（那一轮的 assembly 已经带 `spec:policy` 段落）。这样命令的回执只说「模式开了、草稿在
哪」，不会替用户开题。

消息用 `userMessage()` 内联构造（`node:crypto` 的 `randomUUID` + 深冻结），等价于
`@deepseek-ai/dsh-llm` 的 `createUserMessage`，但省掉一个 import。

## 命令实现

`ctx.inject(["commands"], (commandCtx) => commandCtx.commands.register({...}))`——
`commands` 是可选服务，缺席时插件仍能激活（只是进不去模式）。

`definitionId: "dsh-spec-mode"` 是给客户端做身份识别用的；本插件不依赖它，
斜杠菜单也不会因此给图标（见「插件说明」）。

handler 顺序：

1. `message === "off"` → `loggedActive` 为假就回「未开启」；否则注入退出提醒并回执。
2. 未在模式里 → 查 `ctx.get("planMode")?.get(agent).active`，活跃则回错误，状态不变。
3. `liveExits.delete(session)`、`ensureParentDir(draftPath)`。
4. 有想法/附件 → `steer`；否则**什么都不提交**（裸 `/spec` 只切模式）。

状态一律**由 `command/run` + `command/done` 承载**，handler 自己不写任何状态——这是
「内存状态始终由会话日志派生」的落点，避免两处真相。

## 退出确认（`spec_resolve`）

工具**常驻注册**（不设 `deferLoading`）：进出模式只换提示词段落，不换工具目录，KV cache
前缀因此更稳；也避免「收尾这种必需步骤要靠搜索命中」。

```
exec.agent 缺席              → 抛错
该会话不在 spec mode         → 抛错
ctx.get("userQuestions") 缺席 → 抛错（fail closed，让用户走 /spec off）
ask({ questions: [...], agent, signal: exec.signal })
  ├─ ASK_CANCELLED（用户关掉面板） → 抛错：「保持开启，停下等他的消息」
  ├─ 选了「退出并落盘」            → liveExits.add(session)，返回 { exited: true, draftPath }
  └─ 其它（继续访谈 / 自定义文本）  → 抛错：明确「不要重复调用本工具」
```

抛错即 `tool/result` 带 `isError: true`，投影据此清掉 `exitCall`、`active` 不变——
「用户拒绝」不需要额外的事件类型。

`ASK_CANCELLED` 用鸭子类型判（`cause.code`），不用 `instanceof UserQuestionError`：
后者要求 import `@deepseek-ai/dsh-user-questions`，而本插件刻意零依赖。

工具的输出 schema 是 `{ exited: true, draftPath }`，`render` 直接给出落盘三步，避免模型
凭记忆排序。

## 设计取舍

| 取舍 | 理由 |
| --- | --- |
| bash/pwsh 不拦 | 与 DSH plan mode 一致：拦 shell 需要解析语义，误伤成本高于收益 |
| AGENTS.md 检查只警告 | 行数是内容质量判断，官方对计划内容同样零代码检查 |
| 提示词承载访谈协议 | 提问方式、理解质量无法机器判定 |
| 状态按会话分键 | 一个进程内多个会话（含子代理）共用同一份模块实例 |
| 草稿在 `docs/` 而非 harness home | 草稿是项目文档的一部分，要随仓库版本化 |
| 退出确认走注册工具 | 访谈收尾由模型发起：模型知道访谈是否结束，用户只需在确认框里选是/否 |
| `/spec off` 不弹确认 | 与 DSH plan mode 对齐；确认框留给模型发起的收尾 |
| 零 `@deepseek-ai/*` 依赖 | bundle 是 `link:` 进 profile 的，Node 从包自身位置解析 import；引了就得在 package.json 里声明依赖，等于装第二份运行时（zod / cordis / dsh-tools 各一份） |
| 不做 Client 半 | 状态指示需要客户端插件消费 `wire.view`；本版本先交付可用的 Host 半 |
| 不声明 Config | `Config` 必须是 schemastery schema，会引入依赖；先做成代码常量 |

## 依赖的宿主 API

全部是运行时从 `ctx` / `agent` / `session` 上取的实例成员，没有 import：

| 来源 | 用到什么 |
| --- | --- |
| `ctx.sessionProjections` | `register(definition)`、`stateOf(session, key)` |
| `ctx.systemPrompt` | `section({name, order, text})`、`getSectionOrder('PLAN_POLICY')` |
| `ctx.commands` | `register({definitionId, name, description, input, handler})` |
| `ctx.tools` | `register(definition)`、`guard(fn)` |
| `ctx` 事件 | `on('tools/post-execute', (exec, result, next))`、`on('agent/created', ({agent}))` |
| `ctx` 其它 | `inject(['commands'], cb)`、`get('planMode')`、`get('userQuestions')` |
| `agent` | `session`、`inject(msg)`、`steer(msg)` |
| `session` | `header.cwd`、`header.origin`、`header.delegationDepth` |
| `exec`（工具/守卫） | `agent`、`name`、`arguments`、`signal` |
| `userQuestions.ask()` | `{ questions, agent, signal }` → `{ answers: [{ id, selected, custom }] }` |

宿主升级后若这些签名变动，先跑「交接文档」里的验证清单。
