## 设计沿革（为什么是现在这样）

1. **为什么不用自定义会话事件。** 原插件用宿主提供的自定义会话条目 API 写状态。
   DSH 的 `SessionEventMap` 可以声明合并，但读路径只认
   `KNOWN_SESSION_EVENT_TYPES` 这个生成闭集，除非信封带 `ignorable: true`，而
   `Session.append()` 设不了该标记——写进去这份日志之后打不开。改为 fold 既有事件。
2. **为什么不引 `@deepseek-ai/*` 依赖。** bundle 是 `link:` 进 profile 的，Node 从包
   自身位置解析 import。要引 `@deepseek-ai/dsh-tools` 就得在 package.json 里声明依赖，
   pnpm 会装第二份 `dsh-tools` / `zod` / `cordis`，而且 `instanceof` 跨副本会失效。
   于是 `defineTool`、`createUserMessage`、`brandString` 全部内联等价实现。
3. **为什么工具定义是手写的。** 因为不引 `defineTool`。手写要满足的其实很少：
   `ctx.tools.register()` 只校验 `output` 形状与 `output.schema` 的 JSON Schema 子集
   （`assertSupportedJsonSchema`），参数 schema 直接透给模型。参数校验是 `defineTool`
   自己包的，本工具无参数，不需要。
4. **为什么 `/spec off` 不弹确认。** 与 DSH plan mode 对齐；确认框留给模型发起的收尾
   （`spec_resolve`），那才是真正需要用户裁决的一步。
5. **为什么不做 Client 半。** 状态指示需要客户端插件消费投影的 `wire.view`
   （参考 `@deepseek-ai/dsh-client-ui-plan`）。先交付可用的 Host 半，客户端留作后续。
6. **为什么图标改过一版。** 初版 `icon.svg` 用了 `stroke="currentColor"`。图标是以
   `data:` URL 塞进 `<img>` 渲染的，SVG 自成一个文档、拿不到宿主 CSS 的 `color`，
   `currentColor` 落到初始值黑色，深色主题下等于没有图标。内置插件一律用显式颜色，
   已照此重写。

## 常见改动 → 改哪里

| 想改什么 | 改哪 |
| --- | --- |
| 访谈协议措辞、七项字段、落盘顺序 | `prompt.js` 的 `specModeContext()` |
| 草稿文件名 / 目录 | `state.js` 的 `DRAFT_DIR` / `DRAFT_BASENAME` |
| 草稿锚点规则 | `state.js` 的 `findProjectAnchor()` |
| 哪些工具被拦、放行范围 | `index.js` 的 `ctx.tools.guard()` + `guard.js` 的 `classifyTarget()` |
| 退出确认工具的行为 / 文案 | `index.js` 的 `ctx.tools.register()` + `prompt.js` 的落盘小节 |
| 新增工具入参路径键 | `guard.js` 的 `PATH_KEYS` |
| 拦截文案 | `index.js` 里 guard 返回的 `reason` 字面量 |
| AGENTS.md 检查项 / 阈值 | `advisories.js` |
| 跨会话提醒文案 | `prompt.js` 的 `pendingDraftNotice()` |
| 命令描述、回执文案、确认文案 | `index.js` 的 `commands.register()` |
| 图标 | `icon.svg`（显式颜色，别用 `currentColor`；`package.json` 的 `icon` 指向它） |
| 投影状态字段 / fold 语义 | `state.js` 的 `createSpecProjection()`，**同时把 `PROJECTION_VERSION` 加一** |

包是 `link:` 进 profile 的，改文件后 HMR 会重载；若没生效，重开 `dsh web`。
改投影语义而不 bump `PROJECTION_VERSION`，会让持久化缓存里的旧行被前向 fold 成垃圾。

## 验证清单

手工步骤，逐条对应一个可观察结果。第 1 条已实测；第 2 条只验证了菜单里出现 `spec`
这一半，回执与后续都还没跑；第 3 条起全部待验证。

1. **加载**：`plugin_manager list_plugins` 里 `include:spec-mode` 是
   `enabled: true, fiberPhase: active`。
2. **进入**：输入框打 `/`，菜单里出现 `spec`（无图标，属预期）。
   - 裸 `/spec` → 回执 `Spec mode on. 工作树只读；直接发消息即可开始访谈。草稿：…`，
     **对话里不出现任何消息、模型不启动**；随后随便发一条消息 → 模型按协议开始访谈。
   - `/spec 做一个 X` → 回执 `Spec mode on. 草稿：<项目根>/docs/spec-draft.md`，
     想法成为这一轮的用户消息，模型立刻开始访谈。
3. **草稿位置**：在**没有 `.git`** 的目录里重复第 2 条 → 草稿落在
   `<该目录>/docs/spec-draft.md`（不是 `~` 下）。
4. **守卫**：让模型 `write README.md` → 工具返回 `Spec mode: 工作树只读。…`，
   确认文件未创建。
5. **放行边界**：让模型 `write docs/notes.md` → 同样被拦（只有草稿本身可写）。
   再让它 `write <草稿绝对路径>` → 成功。
6. **互斥**：本 profile 里 plan mode 是禁用的，这条要先启用 `plan-mode` 行才能测。
7. **退出**：让模型调用 `spec_resolve` → 弹确认框
   - 选「继续访谈」→ 工具结果写明不要重复调用；状态栏无变化（本版无状态栏）；
     `write` 仍被拦。
   - 选「退出并落盘」→ 回执给出三步；同一轮内写出 AGENTS.md 与 docs/*.md、草稿被删除；
     此后 `write` 不再被拦。
   - 手动入口：`/spec off` → 回执 `Spec mode off. 草稿保留在 …`，`write` 恢复。
8. **跨会话**：保留草稿，开一个新会话随便问一句 → 模型应提到那份草稿，并对照 `AGENTS.md`
   与 `docs/` 下已落盘的文档判断它是否已被取代：已取代的应被删掉，未被取代的才接着访谈。
9. **软约束**：让模型写一份 >200 行的 `AGENTS.md` → 工具结果里带行数警告，写入成功。
10. **持久化**：`/spec` 后关掉会话再 resume → 模式仍开启（投影从日志恢复）。

## 坑

- **`command/run` 在 handler 之前入日志。** handler 里判「本来是否开启」必须用
  `loggedActive()`，用 `isSpecActive()` 会读到本次选择本身。实测踩到过，
  `selftest.mjs` 有断言锁这条。
- **批准退出后同轮写入靠进程内旁路。** `liveExits` 只保证同一轮的即时判定；durable
  真相是 `tool/result` 的 fold。别把 `liveExits` 当成状态来源。
- **`currentColor` 等于没有图标。** 见「设计沿革」第 6 条。
- **投影 key `spec` 是全局唯一的。** 与别的插件撞 key 且 `stateVersion` 不同会抛错；
  相同则共享同一份 fold。改名要连带 `PROJECTION_KEY` 与文档一起改。
- **`state.js` 的 `apply()` 必须对无关事件返回同一引用。** 返回新对象会让每次事件都
  产生下游工作，投影缓存的增量机制失效。
- **`ctx.tools.guard()` 是全局的。** 它按 `exec.agent.session` 取状态，所以不会误伤别的
  会话；但也意味着状态读取必须廉价——目前每次 `write`/`edit` 会走一次
  `findProjectAnchor()`（几次 `existsSync`），可以接受，改成缓存前先量。
- **`ctx.systemPrompt.section()` 的 provider 抛异常会打断整个 assembly。** 已包
  try/catch 返回空串。
- **`input.hint` 影响菜单可见性。** `dsh-client-ui-commands` 会按
  `position === "argued"` 过滤没有 `hint` 的行；本命令的 `hint` 是 `'[off|初始想法]'`。

## 未做的事 / 已知缺口

- bash/pwsh 写文件不拦（与 DSH plan mode 同构，刻意取舍）
- 子代理工具集不裁剪（plan mode 会裁剪）
- 草稿删除/改名保护在默认工具集下休眠
- 模式互斥单向（plan mode 不知道 spec mode 存在）
- 落盘顺序仍是模型驱动，没有代码校验
- 草稿不会被自动清理，靠协议要求在确认后删除
- 没有 UI 状态指示（无 Client 半）
- 没有 Config，全部是代码常量
- 相对路径草稿按会话 cwd 判定，与沙箱 workspaceRoot 不同基准时是已知边界

## 上游风险

依赖的宿主 API 全部列在 `实现逻辑.md` 末节。宿主升级后先跑验证清单第 1、4 条——
这两条同时覆盖 API 装配与拦截生效。

另有两条与上游实现细节耦合、升级时需要重看的地方：

- **投影注册表契约**：`register()` 只校验 `stateVersion` 是非负整数、同 key 同版本；
  `stateSchema` 只在恢复持久化缓存行时被 `parse`。本插件用的是鸭子类型的
  `{ parse }`，不是真 zod schema——上游若开始要求真 schema，这里要跟着换。
- **客户端命令菜单**：斜杠菜单不给 Host 命令行图标这件事写在
  `dsh-client-ui-commands` 的 `candidates()` 与 `HOST_FACES` 里。若上游开放了图标通道，
  本插件可以直接受益，不需要改代码。
