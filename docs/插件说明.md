# Spec Mode 插件说明

一个 DSH bundle 插件，提供 `/spec` 模式：由模型主导的增量访谈，把用户逐步浮现的需求
固化成 **AGENTS.md 规则** + **`docs/` 技术文档**。

- 包目录：`C:\Users\1\Downloads\tmp\dsh-spec\dsh-spec-mode\`
- 入口：`index.js`（Host 插件，`export function apply(ctx)`）
- 依赖：仅 `node:crypto` / `node:fs` / `node:os` / `node:path`。**不 import 任何
  `@deepseek-ai/*` 包**，所以它只靠 profile 自身就能解析，不会装出第二份 Harness 运行时。
- 安装形态：`link:` 进 profile `web`，Loader 行为 `include:spec-mode`。

## 解决的问题

用户无法一次说清需求，会分多次追加。现有能力都不合适：

| 现有能力 | 为什么不合适 |
| --- | --- |
| plan mode | 只产出计划，工作树不设只读守卫，也没有「草稿 → AGENTS.md + docs/」的落盘目标 |
| skill | 被动内容，无状态、无强制、无流程控制 |
| 普通对话 | 访谈结论留在对话里，会被压缩丢失；跨会话无法续谈 |

Spec mode 给出的是**模式**：显式命令进入、会话持久状态、结构化路径守卫、模式提示词注入。

## 使用

```
/spec [初始想法]        # 进入；带想法时想法作为这一轮的用户消息提交
/spec off               # 退出，工作树恢复可写，草稿保留
```

| 当前状态 | `/spec` 的行为 |
| --- | --- |
| 未启用 | 进入。解析草稿路径、建 `docs/` 目录、状态落进会话日志、注入访谈协议（走系统提示词段落，不展开在对话里） |
| 已启用 | 视为继续访谈：带想法就提交这一轮，不带想法就起一轮让模型问下一个问题 |
| 已启用 + `/spec off` | 退出，工作树恢复可写，草稿保留 |
| plan mode 活跃 | 拒绝，回 `Exit plan mode first.`，状态不变 |

访谈结束时**不需要用户手动退出**：模型调用 `spec_resolve` 工具，弹出确认框让用户选。

| 用户选择 | 结果 |
| --- | --- |
| 退出并落盘 | 退出模式、工作树可写；工具结果指示模型在同一轮落盘 |
| 继续访谈 | 模式不变、工作树仍只读；工具结果写明「不要重复调用」 |
| 关掉确认框 | 同上，并告诉模型用户在插话，停下等消息 |
| 没有 userQuestions 通道 | fail closed：模式不变，让用户运行 `/spec off` |

`/spec off` 是手动退出的备用入口。

## 访谈期间的行为

**工作树只读。** 唯一可写目标是草稿 `<项目根>/docs/spec-draft.md`；项目根 = 最近的
`.git`（与 `@deepseek-ai/dsh-agent-instructions` 的 `projectRootMarkers` 默认值一致），
没有则用会话工作目录。

草稿结构对齐最终目标文件，便于「搬移而非重写」：已确定 / 假设（待用户确认）/ 未决。
协议全文见 `prompt.js` 的 `specModeContext()`，要点：

- 每轮回答**立刻**写进草稿，而不是访谈结束后统一写
- 已确定的字段不重问；追加时增量合并
- 一次问几个不限——只要每个问题都在补齐**用户侧信息**，而不是确认模型已形成的判断
- 每轮做**回述确认**：用自己的话复述理解（含推出但用户没明说的结论）
- 七项字段（目标与验收 / 技术选型 / 实现路径 / 边界条件 / 验证方式 / 规则 / 文档）
  全部覆盖**且用户确认过回述**，才算访谈完成
- 每轮结尾输出状态行 `已定：… ｜ 待定：… ｜ 假设：…`

## 强制与警告清单

强制力度沿用原插件的分界线：**结构性、可确定性判定、误判代价高 → 代码强制；
内容质量、需要判断 → 提示词或警告**。

| 约束 | 强度 | 机制 |
| --- | --- | --- |
| 工作树 `write` / `edit` | **阻止** | `ctx.tools.guard()` 路径谓词 |
| 模式开启期间写 AGENTS.md / `docs/*.md` | **阻止** | 同上（它们是工作树写入，落盘在退出后进行） |
| 删除 / 改名草稿 | **阻止** | 工具名 `/^(delete\|remove\|move\|rename)/i` + 路径命中草稿 |
| 退出 spec mode | 用户确认 | `spec_resolve` 工具走 `ctx.userQuestions.ask()` |
| plan mode 活跃时进入 | **阻止** | 读 `ctx.planMode.get(agent).active`（该服务缺席时静默跳过） |
| AGENTS.md > 200 行 | 警告 | `tools/post-execute` 挂一条 `additionalContexts`，写入照常成功 |
| bash/pwsh 写文件 | 不拦 | 与原插件、与 DSH plan mode 一致：代码只守卫结构化写原语 |
| 提问方式、理解质量、落盘顺序 | 提示词 | 与 plan mode 对计划内容同样零代码检查 |

`local://` / `artifact://` 等 `scheme://` 设备路径一律放行——它们不是工作树写入。

## 退出后

落盘在**退出 spec mode 之后**做。协议要求模型：先做整体回述 → 调用 `spec_resolve`
让用户确认退出 → 用户选「退出并落盘」后按固定顺序落盘，不跳步：

1. **AGENTS.md** — 只放两块内容：文档索引（路径 + 何时读）、规则（每条可证伪并标注
   enforcement）；不设 Project / Language & Style 等章节，正文写进 docs/ 对应文档
2. **docs/** — 文档集合由访谈第 7 项定，不是固定清单；写不出内容的类型不写，也不留
   占位文件。协议给出常见类型菜单，允许自造
3. 确认后删除草稿——留着会变成第二份真相来源

文档同步条款固定写进 AGENTS.md 的规则块（它是一条规则，不是新章节）。

## 界面：这个插件在哪些地方出现

| 界面 | 表现 |
| --- | --- |
| 输入框 `/` 命令菜单 | 一行 `spec`，描述为命令的 `description`，**没有图标**（见下） |
| 命令执行回执 | `/spec` → `Spec mode on. 草稿：<路径>`；`/spec off` → `Spec mode off. 草稿保留在 <路径>` |
| 对话流 | 只出现工具调用与用户消息；协议文本走系统提示词，不占对话 |
| 设置 → 插件 | 卡片/列表/详情读取 `meta.icon` 与 locale 的标题、描述（元数据已实测读取成功；页面渲染未目视确认） |

### 斜杠菜单里为什么没有图标

`dsh-client-ui-commands` 的 `candidates()` 对 Host 命令目录行只推
`{ name, description, hint? }`；图标只来自它自己的 `HOST_FACES` 硬编码表
（`goal` / `plan` / `feedback` / `compact` / `permission` / `export` 六个内置
`definitionId`）或客户端贡献的 `CommandContribution.icon`。三条路都被堵死：

1. Host 的 `CommandDefinition` 没有 icon 字段，客户端也不读。
2. 客户端贡献能带 `icon`，但同名会**抛错**：
   `ui-commands: contribution /spec collides with a host command`。
3. 客户端贡献没有 `input.hint`，会被 `position === "argued"` 过滤——`/spec 做一个 X`
   这种带参形式会失效。为一个图标把命令降级不划算。

要真让这一行有图标，只能改上游：把 `spec` 加进 `dsh-client-ui-commands` 的 `HOST_FACES`。

## 已知限制

- **bash/pwsh 不拦**：`echo > file` 能绕过守卫。与 DSH plan mode 同构，属刻意取舍。
- **互斥是单向的**：本插件会拒绝在 plan mode 活跃时进入；反过来 plan mode 不知道
  spec mode 的存在。本 profile 里 plan mode 是禁用的，所以该检查目前休眠。
- **子代理不受限**：spec mode 的状态按会话日志分键，子代理会话没有 `/spec` 记录，
  所以不会被拦；与 OMP 版一致。
- **草稿删除保护可能休眠**：当前工具集里没有 `delete`/`move`/`rename` 命名的工具，
  该分支只在存在这类工具时生效。
- **落盘仍是模型驱动的**：`spec_resolve` 只保证「退出要经用户确认」，落盘顺序靠协议与
  工具结果文本约束，没有代码校验。
- **没有 UI 状态指示**：OMP 版会在状态栏显示 `spec`。DSH 里做这件事需要额外的 Client
  插件（参考 `@deepseek-ai/dsh-client-ui-plan` 消费 `plan` 投影的 `wire.view`），
  本版本只做 Host 半。
- **没有 Config**：协议文本、草稿文件名、200 行预算都是代码常量。要做成可配置需要引入
  `@deepseek-ai/schemastery` 作为依赖，这一版刻意不引。
- **相对路径草稿按会话 cwd 判定**：宿主写文件时可能以沙箱 workspaceRoot 为基准。两者
  不同时，`docs/spec-draft.md` 这个相对写法可能被判成草稿而实际写到别处。协议因此要求
  一律用绝对路径；改这块要一起看 `guard.js` 的 `classifyTarget()`。
