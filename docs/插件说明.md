# Spec Mode 插件说明

一个 DSH bundle 插件，提供 `/spec` 模式：由模型主导的增量访谈，把用户逐步浮现的需求固化成
**开发规范**与**项目文档**。

这份文档回答一个问题：这个插件做什么、怎么用、拦什么不拦什么、界面出现在哪、有哪些限制。读者
是安装它、或想知道它能不能满足自己需求的人——读完你会知道该在什么时候用它、它会挡住哪些操作、
以及它做不到哪些事。不需要先读别的文档。

- **包目录**：本仓库根目录
- **入口**：仓库根目录的入口模块，一个接收插件的上下文、把各种能力挂上去的装配函数
- **依赖**：只用到 Node 自带的加密、文件、环境、路径四类模块。不装任何宿主运行时包，所以只靠
  profile 自身就能解析
- **安装形态**：以链接方式挂进 web profile，加载器的行为名是 include:spec-mode

## 解决的问题

用户无法一次说清需求，会分多次追加。现有能力都不合适：

| 现有能力 | 为什么不合适 |
| --- | --- |
| 计划模式 | 只产出计划，工作树不设只读守卫，也没有「草稿变成规范与文档」的落盘目标 |
| 技能 | 被动内容，无状态、无强制、无流程控制 |
| 普通对话 | 访谈结论留在对话里，会被压缩丢失；跨会话无法续谈 |

Spec mode 给出的是**模式**：显式命令进入、会话持久状态、结构化路径守卫、模式提示词注入。

## 使用

```
/spec [初始想法]
/spec off
```

| 当前状态 | `/spec` 的行为 |
| --- | --- |
| 未启用 + 无参 | 只进入模式。解析草稿路径、建文档目录、状态落进会话日志、注入访谈协议（走系统提示词段落，不展开在对话里）；**不提交任何消息**，访谈从用户随后发的第一条消息开始 |
| 未启用 + 带想法 | 进入模式，并把想法作为这一轮的用户消息提交，访谈立刻开始 |
| 已启用 + 带想法 | 想法提交为这一轮的用户消息 |
| 已启用 + 无参 | 只回执，不提交消息；模型在用户下一条消息里继续访谈 |
| 已启用 + `/spec off` | 退出，工作树恢复可写，草稿保留 |
| 计划模式活跃 | 拒绝，回一句「先退出计划模式」，状态不变 |

访谈结束时**不需要用户手动退出**：模型调用退出确认工具，弹出确认框让用户选。

| 用户选择 | 结果 |
| --- | --- |
| 退出并落盘 | 退出模式、工作树可写；工具结果指示模型在同一轮落盘 |
| 继续访谈 | 模式不变、工作树仍只读；工具结果写明「不要重复调用」 |
| 关掉确认框 | 同上，并告诉模型用户在插话，停下等消息 |
| 组合里没有提问通道 | fail closed：模式不变，让用户运行 `/spec off` |

`/spec off` 是手动退出的备用入口。

## 访谈期间的行为

**工作树只读。** 唯一可写目标是草稿，仓库相对路径是 docs/spec-draft.md；项目根取最近的版本库
目录，没有就用会话工作目录。

草稿结构对齐最终目标文件，便于「搬移而非重写」：已确定 / 假设（待用户确认）/ 未决。协议全文在
注入文本里，要点：

- 每轮回答**立刻**写进草稿，而不是访谈结束后统一写
- 已确定的字段不重问；追加时增量合并
- 一次问几个不限——只要每个问题都在补齐**用户侧信息**，而不是确认模型已形成的判断
- 每轮做**回述确认**：用自己的话复述理解（含推出但用户没明说的结论）
- 七项字段（目标与验收 / 技术选型 / 实现路径 / 边界条件 / 验证方式 / 开发规范 / 文档）
  全部覆盖**且用户确认过回述**，才算访谈完成
- **产出文档要说人话**（硬要求）：默认读者是既不懂代码也不懂这个业务的人——术语可以用、命令
  可以有，但正文不出现代码；首段是白话导读，术语首次出现当句解释
- **决策只记结论**：只写定了什么、约束谁、怎么用，不写被否决的方案与「为什么不选别的」
- **自举**：落盘的开发规范里固定带走四条文档规则，之后在这个仓库干活的人继续照着写
- 每轮结尾输出状态行 `已定：… ｜ 待定：… ｜ 假设：…`

## 强制与警告清单

强制力度沿用原插件的分界线：**结构性、可确定性判定、误判代价高 → 代码强制；
内容质量、需要判断 → 提示词或警告**。

| 约束 | 强度 | 机制 |
| --- | --- | --- |
| 工作树写入 | **阻止** | 工具守卫按路径判定 |
| 模式开启期间写规范文件或文档 | **阻止** | 同上（它们是工作树写入，落盘在退出后进行） |
| 删除 / 改名草稿 | **阻止** | 工具名以删除、移动、改名开头 + 路径命中草稿 |
| 退出模式 | 用户确认 | 退出确认工具走宿主的提问通道 |
| 计划模式活跃时进入 | **阻止** | 读宿主计划模式的启用状态（该服务缺席时静默跳过） |
| 规范文件超过 200 行 | 警告 | 写入落盘后挂一条提醒，写入照常成功 |
| 规范里缺文档规则块 | 警告 | 同上：四条文档规则（过时同步 / 不写代码 / 白话导读 / 决策只记结论）缺哪条报哪条 |
| 文档首段不是外行导读 | 警告 | 同上：第一个小节标题之前没有一段 24 字以上、不含反引号与路径的纯白话 |
| 文档里出现源码块或代码引用 | 警告 | 同上：源码块、反引号里的标识符、函数名、常量、调用形式；命令与清单表格里的文件名不算 |
| 文档里写了被否决方案 | 警告 | 同上：标题、加粗标签或列表项命中拒绝词表（表格行不算） |
| 访谈草稿 | 不检查 | 草稿是中间产物，落盘时删除，检查前按路径排除 |
| 用 shell 写文件 | 不拦 | 与计划模式一致：代码只守卫结构化写原语 |
| 提问方式、理解质量、落盘顺序 | 提示词 | 与计划模式对计划内容同样零代码检查 |

文档形式的外部路径（local:// 这类设备路径）一律放行——它们不是工作树写入。

## 退出后

落盘在**退出 spec mode 之后**做。协议要求模型：先做整体回述 → 调用退出确认工具让用户确认退出
→ 用户选「退出并落盘」后按固定顺序落盘，不跳步：

1. **开发规范文件** — 只放两块内容：文档索引（路径 + 何时读）、**可证伪的开发规范规则**（每条
   标注是代码强制还是提示词）；开头一句话说明这份文件是什么、给谁看；不设项目简介、语言风格之类
   的章节，正文写进文档目录里对应那份。
   归属判据：这条规则换了实现就失效吗？会 → 产品特性，进文档；不会 → 开发规范，进规范文件
2. **文档目录** — 访谈中浮现的产品特性（行为边界、对外契约、结构决策）住在这里；决策只记结论，
   不记被否决方案与理由；文档集合由访谈第 7 项定，不是固定清单；写不出内容的类型不写，也不留
   占位文件。每份文档首段是外行导读，术语可用、命令可有、代码不出现；协议给出常见类型菜单，允许
   自造
3. 确认后删除草稿——留着会变成第二份真相来源

文档规则块固定写进规范文件（它是一块规则，不是新章节）：改代码前同步过时文档、文档不写代码、
首段白话导读、决策只记结论。这叫自举——插件自己的文档要求跟着产出文件传下去。

## 界面：这个插件在哪些地方出现

| 界面 | 表现 |
| --- | --- |
| 输入框的命令菜单 | 一行 spec，描述取命令自己带的描述，**没有图标**（见下） |
| 命令执行回执 | 无参进入 → 一句「模式已开、工作树只读、直接发消息即可开始访谈」加草稿路径；带想法进入 → 一句「模式已开」加草稿路径；退出 → 一句「模式已关」加草稿保留位置 |
| 对话流 | 只出现工具调用与用户消息；协议文本走系统提示词，不占对话。裸 `/spec` 不产生任何对话消息 |
| 设置里的插件页 | 卡片、列表与详情读插件元数据里的图标与多语言文案（元数据已实测读取成功；页面渲染未目视确认） |

### 命令菜单里为什么没有图标

宿主的命令菜单只向客户端推命令名、描述与输入提示；图标只来自客户端自己硬编码的一张内置表，或
客户端贡献的命令。三条路都被堵死：

1. 宿主命令定义里没有图标字段，客户端也不读它。
2. 客户端贡献可以带图标，但同名会**抛错**，说与宿主命令冲突。
3. 客户端贡献没有输入提示，带参形式会被过滤掉——`/spec 做一个 X` 这种写法会失效。为一个图标
   把命令降级不划算。

真要让这一行有图标，只能改上游：把这个命令加进宿主命令菜单的硬编码图标表。

## 已知限制

- **用 shell 写文件不拦**：重定向写文件能绕过守卫。与计划模式同构，属刻意取舍。
- **互斥是单向的**：本插件会拒绝在计划模式活跃时进入；反过来计划模式不知道 spec mode 的存在。
  本 profile 里计划模式是禁用的，所以该检查目前休眠。
- **子代理不受限**：spec mode 的状态按会话日志分键，子代理会话没有进入记录，所以不会被拦；
  与原插件一致。
- **草稿删除保护可能休眠**：当前工具集里没有以删除、移动、改名开头的工具，该分支只在存在这类
  工具时生效。
- **落盘仍是模型驱动的**：退出确认工具只保证「退出要经用户确认」，落盘顺序靠协议与工具结果文本
  约束，没有代码校验。
- **提醒是近似判定**：只检查首段是不是白话、有没有源码块与代码引用、有没有把否决理由写成小节；
  整篇读不读得懂仍是模型判断。误报只挂一条提醒、不阻止写入。
- **提醒只在 spec 工作期间挂出**：规范文件的行数预算不判模式；其余提醒只在模式开启中、本轮刚
  批准退出、或草稿还在盘上时出现，并排除草稿本身。装了插件但没在用 spec mode 的项目，写自己的
  文档不会被提醒。
- **没有界面状态指示**：原插件会在状态栏显示 spec。DSH 里做这件事需要额外的客户端插件，本版本
  只做宿主半边。
- **没有配置项**：协议文本、草稿文件名、行数预算都是代码常量。要做成可配置需要引入宿主的配置
  依赖，这一版刻意不引。
- **相对路径草稿按会话工作目录判定**：宿主写文件时可能以沙箱的工作区根为基准。两者不同时，
  docs/spec-draft.md 这个相对写法可能被判成草稿而实际写到别处。协议因此要求一律用绝对路径；
  改这块要一起看路径判定的实现。
